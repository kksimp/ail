# Constraints on a fully custom toolchain

> **Non-normative design note,** 2026-10-04. It lists the places where
> [ADR 0009](../decisions/0009-custom-tooling-policy.md) (custom tooling) and
> [ADR 0010](../decisions/0010-no-llvm-backend.md) (no LLVM) run into hard
> external limits, so the designer can plan around them.

## 1. Unavoidable external dependencies

These can't be replaced by custom tools because the operating system or
platform owner requires them.

| Constraint | Why | Effect |
|---|---|---|
| **macOS: must call `libSystem.dylib`** | Apple doesn't keep the raw syscall interface stable between releases. Go switched from raw syscalls to libSystem (Go 1.11) for this reason. | The macOS runtime links dynamically to libSystem. AIL can still avoid its *C-level* conveniences and call only the needed entry points. |
| **Windows: must call `ntdll.dll` / `kernel32.dll`** | Windows syscall numbers change between builds and are undocumented. | The Windows runtime imports from system DLLs. Import tables are generated by AIL's own linker, so no Microsoft import libraries are needed. |
| **Linux: none** | The Linux syscall ABI is stable. | The Linux runtime **can be completely free of libc** (raw syscalls), which gives full control and static binaries. (Decision needed, OQ-014.) |
| **macOS ARM64: every executable must be code-signed** | The kernel refuses to run unsigned ARM64 code. Ad-hoc signing is enough locally. | AIL's linker must write an ad-hoc code signature itself. This is doable and documented. |
| **macOS distribution: notarization** | Gatekeeper requires Apple's notarization service for downloaded apps. | An external Apple service. It can be automated, not replaced. |
| **Windows distribution: Authenticode / SmartScreen** | Unsigned binaries trigger warnings. | Needs a code-signing certificate. AIL can write the signature itself, but the certificate comes from a CA. |
| **OS loaders and formats** | ELF, PE/COFF and Mach-O are defined by the OS. | AIL writes these formats itself, but has to follow them exactly. |
| **Debug info formats** | Native debuggers and crash tools expect DWARF (Linux, macOS) and PDB/CodeView (Windows). | Write custom DWARF and PDB emitters for compatibility with existing tools, *in addition to* AIL's own richer debug format for the AIL debugger and AI API. |
| **Unwinding tables** | The OS and system debuggers use them: Windows `.pdata`/`.xdata`, DWARF CFI, and Apple's compact unwind. | Must be emitted for the OS to walk stacks (exceptions in FFI, crash reports, profilers). |
| **C ABI for FFI** | Fixed by each platform: System V for x86-64, AAPCS64 for ARM64, Windows x64, and Apple's ARM64 variant. | AIL's backend implements all of them. Clang can serve as a differential-testing oracle (ADR 0010). |

## 2. What "fully custom" means for the toolchain inventory

Components AIL has to build because there's no LLVM and no external tools
(ADR 0009, ADR 0010):

| Component | Notes |
|---|---|
| Lexer, parser, AST, type checker | As planned |
| High-level and low-level IR, optimizer | As planned |
| Instruction selection, register allocation, scheduling | Both ISAs |
| **Assembler / machine-code encoder** | x86-64 (incl. VEX/EVEX) and ARM64 |
| **Linker** | ELF, PE/COFF and Mach-O, including the macOS code signature and Windows import tables |
| **Debug info emitters** | DWARF, PDB, and the native AIL format |
| **Unwind info emitters** | DWARF CFI, Windows unwind codes, Apple compact unwind |
| Runtime, GC, scheduler, allocator | Per OS |
| Standard library | No libc on Linux (pending OQ-014) |
| Formatter, language server, package manager, build system | As planned |
| Debugger, profiler | Per OS. Uses ptrace, the Windows Debug API, and Mach task ports. |
| C header importer (for FFI) | Needs a C parser. Clang isn't allowed as a dependency, so a **custom C parser** for headers is needed. This is significant work, because system headers use many compiler extensions. |

## 3. The bootstrap problem

Something has to compile the first AIL compiler. Options are tracked in
OQ-010 and OQ-013. The custom-tooling policy applies to AIL's **product**.
The language used to write the bootstrap compiler is a separate question,
and that compiler is thrown away once AIL can compile itself (if
self-hosting is chosen).

## 4. Effort implications (honest)

- The first native binary is **months later** than with LLVM. The Stage 3
  interpreter carries semantic validation until then.
- The linker, debug info and C header importer are each substantial projects.
  Mature linkers and debug-info writers are large, years-old codebases.
- In return, AIL controls every byte and every piece of metadata from source
  to executable. That is what makes performance transparency and the AI
  semantic API complete instead of approximate.
